# 应用托管任务与统一专注执行层设计

## 1. 背景

Ark 当前已经有三类可以进入“专注工作”的内容：

- 用户手动创建的任务，通过 `task_focus` 进入任务专注页。
- Vocab 今日单词，通过 `vocab_today` 进入子应用专注工作。
- ERC 复习，通过 `erc_review` 进入子应用专注工作。

现有实现已经把它们接入同一个前端 `focus-work` 运行时和顶部工作流胶囊，但业务模型仍不统一：

- 用户任务有真实 `task_id`、`focus_logs`、`completion_records`、事件绑定、统计和成就闭环。
- Vocab/ERC 当前更像页面级应用动作，只通过 `focus_work_type` 和 `focus_app_work_logs` 被工作流识别。
- 子应用专注可以记录一段专注时间，但还没有自然进入任务体系、今日计划、事件进度和任务完成记录。
- 弹窗壳已经承担部分公共控制，但暂停、继续、完成语义仍带有类型特判。

本设计将子应用专注工作调整为“应用托管任务”模型：子应用必须先初始化，初始化后自动创建或绑定一条由应用管理的重复任务。后续进入专注工作时，本质上都是执行一条任务，只是不同任务来源渲染不同的专注内容。

## 2. 设计目标

1. 让“专注工作”成为统一执行入口。
2. 让 Vocab/ERC 等子应用专注工作进入任务体系，而不是孤立应用动作。
3. 复用现有任务系统的重复任务与 `completion_records` 能力。
4. 避免应用任务污染用户手动任务列表。
5. 明确初始化、任务生成、专注执行、完成记录、统计和成就之间的关系。
6. 为后续更多子应用接入专注工作提供统一模式。

## 3. 非目标

1. 不在本设计中重写 Vocab 或 ERC 的业务算法。
2. 不把 Vocab 的单个单词或 ERC 的单道题建模为任务。
3. 不要求每天复制一条新的普通任务。
4. 不取消现有任务系统的重复任务和完成记录机制。
5. 不让用户手动任务列表默认混入所有应用托管任务。

## 4. 核心结论

采用“应用初始化后生成应用托管重复任务”的方案。

用户第一次使用某个子应用的专注能力前，必须在子应用中完成初始化。初始化用于填写该子应用生成任务所需的长期配置，并创建或绑定对应的应用托管任务。

应用托管任务本质上仍是 `tasks` 中的一条任务，但带有来源标识：

```ts
source_type: 'user' | 'app';
app_id: 'vocab' | 'erc' | null;
app_task_type: 'vocab_today' | 'erc_review' | null;
app_config_id: string | null;
app_instance_key: string | null;
managed_by_app: boolean;
```

对于 Vocab 今日单词和 ERC 复习，推荐使用“一条重复应用任务 + 每天完成记录”：

- 任务本体长期存在，例如“今日单词”。
- 每天完成时写入 `completion_records`。
- 今日是否完成由现有 completion state 判断。
- 子应用自己的学习进度仍保存在子应用表中。

## 5. 当前任务系统如何被复用

Ark 现有任务系统已经支持重复任务：

- 一次性任务完成后会把 `tasks.status` 置为 `done`。
- 重复任务完成时不必改为永久 done，而是写入 `completion_records`。
- `period_type`、`max_completions_per_period`、`weekday_only` 等字段决定当前周期是否可完成。
- `completion_state.hidden_from_action_list` 决定当前周期完成后是否从行动列表隐藏。

因此应用托管任务不需要新增一套“每日完成”概念。它应复用现有 `completion_records`：

```text
任务：今日单词
来源：Vocab
周期：daily

完成记录：
- 2026-05-15 完成一次
- 2026-05-16 完成一次
- 2026-05-17 完成一次
```

这比每天生成一条任务更适合长期使用。每天生成任务会导致历史任务快速膨胀；重复任务加完成记录则让任务列表保持稳定，同时保留完整历史。

## 6. 初始化模型

### 6.1 初始化定义

初始化是用户启用某个子应用任务能力的动作。它不是开始一次专注，也不是创建今天的一次性任务，而是建立该子应用与任务系统之间的长期协议。

初始化完成后，系统应持久化：

1. 子应用配置。
2. 一条或多条应用托管任务。
3. 子应用任务与配置之间的绑定关系。

### 6.2 初始化状态

子应用首页应至少有以下状态：

1. `uninitialized`
   - 子应用尚未初始化。
   - 显示“初始化”按钮。
   - 不允许开始专注工作。

2. `ready`
   - 已初始化。
   - 今天存在可执行应用任务。
   - 显示“开始今日单词”“继续今日单词”或“开始 ERC 复习”。

3. `completed_today`
   - 已初始化。
   - 对应应用任务今天已经完成。
   - 显示“今日已完成”，可查看记录或继续练习，但不重复完成同一周期任务。

4. `blocked`
   - 已初始化，但当前没有可执行内容。
   - 例如词书为空、没有到期复习题、题库未准备好。
   - 显示具体阻塞原因和修复入口。

5. `config_invalid`
   - 初始化配置引用的资源失效。
   - 例如词书被删除、ERC 范围不存在。
   - 要求用户重新初始化或修复配置。

### 6.3 Vocab 初始化信息

Vocab 初始化应收集：

1. 默认词书或词书范围。
2. 每日新词数量。
3. 每日复习批次或复习上限。
4. 默认专注时长。
5. 是否自动加入今日计划。
6. 可选事件绑定。
7. 可选提醒或计划偏好。

初始化产物：

```text
Task:
  title: 今日单词
  source_type: app
  app_id: vocab
  app_task_type: vocab_today
  managed_by_app: true
  is_recurring: true
  period_type: daily
  max_completions_per_period: 1
```

Vocab 的单词学习进度仍由 Vocab 自己维护。任务只代表“今天完成一次 Vocab 今日单词事项”。

### 6.4 ERC 初始化信息

ERC 初始化应收集：

1. 复习范围，例如全部到期题、错题、指定题库。
2. 每日复习题量或复习目标。
3. 复习规则，例如答错回池、间隔规则。
4. 默认专注时长。
5. 是否自动加入今日计划。
6. 可选事件绑定。
7. 可选提醒或计划偏好。

初始化产物：

```text
Task:
  title: ERC 复习
  source_type: app
  app_id: erc
  app_task_type: erc_review
  managed_by_app: true
  is_recurring: true
  period_type: daily
  max_completions_per_period: 1
```

ERC 的题目作答、正确率、复习间隔仍由 ERC 自己维护。任务只代表“今天完成一次 ERC 复习事项”。

## 7. 应用托管任务与普通任务的关系

应用托管任务与普通任务共享基础任务能力：

- `task_id`
- 任务完成状态
- 周期完成记录
- 专注时长记录
- 事件绑定
- 今日计划
- 统计与成就
- 工作流阶段绑定

但它们有不同的管理边界：

| 维度 | 普通任务 | 应用托管任务 |
| --- | --- | --- |
| 创建方式 | 用户手动创建 | 子应用初始化创建 |
| 内容来源 | 用户填写 | 子应用配置与状态生成 |
| 编辑方式 | 用户可完整编辑 | 用户只编辑计划、事件、提醒等外层属性 |
| 业务进度 | 任务本身 | 子应用内部数据 |
| 默认列表 | 普通任务区 | 应用任务区 |
| 删除语义 | 删除任务 | 停用或重置子应用任务能力 |

应用托管任务不应默认混入普通任务列表。首页和今日计划建议分区展示：

```text
今日任务
- 写论文摘要
- 整理笔记

应用任务
- 今日单词
- ERC 复习
```

如果用户希望把某个应用任务当成普通任务管理，可以提供“显示在普通任务中”或“转换为普通任务”的显式操作，但这不是默认路径。

## 8. 专注执行模型

初始化后，Vocab/ERC 进入专注工作时不再只是提交 `focus_work_type`，而是围绕应用托管任务开始一次执行：

```text
应用托管任务 task_id
-> 创建/进入 focus workflow focus 阶段
-> 打开统一 FocusWorkModalShell
-> 根据 task source 渲染对应内容适配器
-> 结束本轮时写 focus_logs
-> 完成事项时额外写 completion_records
-> 子应用同步写自己的业务进度
```

专注内容适配器由任务来源决定：

- `source_type = user`：渲染普通任务专注内容。
- `app_id = vocab, app_task_type = vocab_today`：渲染 Vocab 今日单词内容。
- `app_id = erc, app_task_type = erc_review`：渲染 ERC 复习内容。

这样 `task_focus` 不再只表示“普通任务专注页”，而是可以演进为“任务执行壳”。具体内容由任务适配器决定。

## 9. 弹窗壳职责

`FocusWorkModalShell` 应承担公共执行控制：

1. 暂停专注。
2. 继续专注。
3. 放弃本阶段。
4. 完成本轮专注。
5. 完成事项并结束专注。
6. 显示计时、记录状态、暂停遮罩、确认态。
7. 向后端提交统一执行结果。

内容组件只负责业务内容：

- Vocab 展示单词、提交记忆结果、报告今日单词是否完成。
- ERC 展示题目、提交答案、报告今日复习是否完成。
- 普通任务展示任务标题、备注、只读细节。

内容组件不直接决定工作流推进；它只上报业务进度和可完成状态。

## 10. 主完成按钮语义

主完成按钮必须区分两个层次：

1. 结束本轮专注。
   - 结束当前执行实例。
   - 推进工作流。
   - 不完成背后的任务。

2. 完成事项并结束专注。
   - 结束当前执行实例。
   - 写入任务完成记录。
   - 对应用任务，还要让子应用确认业务事项已完成。

推荐文案：

| 任务类型 | 主动作 | 完成事项动作 |
| --- | --- | --- |
| 普通任务 | 完成本轮专注 | 完成任务并结束专注 |
| Vocab 今日单词 | 结束本轮专注 | 完成今日单词 |
| ERC 复习 | 结束本轮复习 | 完成今日 ERC 复习 |

对于 Vocab/ERC，内容自然完成时可以触发“完成事项并结束专注”。用户主动点击主动作时，只结束本轮专注，不应默认把当天任务标记完成。

## 11. 暂停、继续与放弃

所有专注执行都应支持暂停和继续，不只普通任务。

暂停语义：

- 当前阶段不结束。
- 当前任务不完成。
- 工作流不推进。
- 计时冻结。
- 内容区遮罩并禁止继续提交业务动作。
- 恢复后继续同一阶段、同一任务、同一内容上下文。

放弃语义：

- 结束当前执行实例。
- 结果记为 `abandoned`。
- 工作流进入后续流转。
- 不写任务完成记录。
- 不回滚已经提交到子应用的数据，例如已背过的单词、已提交的题目。

统计应排除暂停时间。实现上需要显式记录暂停累计时长，或将一次执行拆成多个有效计时片段，避免把暂停时间计入 `focus_logs`。

## 12. 回写规则

### 12.1 普通任务

完成本轮专注：

- 关闭当前 focus log。
- 增加任务 `actual_duration`。
- 不写完成记录。

完成任务并结束专注：

- 关闭当前 focus log。
- 增加任务 `actual_duration`。
- 写 `completion_records`。
- 一次性任务可置为 `done`。
- 重复任务保留任务本体，由 completion state 判断当前周期完成。

### 12.2 Vocab 今日单词

结束本轮专注：

- 关闭当前 focus log。
- 增加应用托管任务 `actual_duration`。
- 保存 Vocab 已经发生的学习进度。
- 不写任务完成记录。

完成今日单词：

- 关闭当前 focus log。
- 增加应用托管任务 `actual_duration`。
- 写 `completion_records`。
- 保存 Vocab 今日完成状态和进度快照。

### 12.3 ERC 复习

结束本轮复习：

- 关闭当前 focus log。
- 增加应用托管任务 `actual_duration`。
- 保存已提交题目的复习结果。
- 不写任务完成记录。

完成今日 ERC 复习：

- 关闭当前 focus log。
- 增加应用托管任务 `actual_duration`。
- 写 `completion_records`。
- 保存 ERC 今日复习完成状态和进度快照。

## 13. 统计、成就与事件

应用托管任务进入 `focus_logs` 后，现有统计可以自然覆盖更多场景：

- 全局专注时长包含普通任务和应用任务。
- 今日专注时长包含所有 `record_focus = true` 的任务执行。
- 事件专注时长可通过应用任务的 `event_id` 归属到事件。
- 成就中的专注时长、连续推进、事件推进可复用任务完成记录和专注日志。

需要注意：应用任务的业务明细，例如背了多少单词、ERC 正确率，不应塞进任务表。它们应留在子应用自己的数据模型中。任务体系只保存执行和完成层面的共同事实。

## 14. 工作流阶段绑定

工作流阶段未来应优先绑定 `task_id`。对于应用任务：

- 预设工作流可以绑定“今日单词”这条应用托管任务。
- 阶段开始时根据任务来源打开对应内容适配器。
- 如果应用任务当天已完成，该阶段应按现有“重复任务当前周期不可完成”的规则跳过或提示选择其他任务。
- 如果应用任务配置失效，该阶段应进入配置修复提示，而不是打开空内容。

`focus_work_type` 可以逐步降级为前端内容适配器信息，而不是主业务身份。主身份应是 `task_id`。

## 15. 数据模型建议

### 15.1 tasks 扩展字段

```text
source_type VARCHAR(20) NOT NULL DEFAULT 'user'
app_id VARCHAR(40) NULL
app_task_type VARCHAR(80) NULL
app_config_id UUID NULL
app_instance_key VARCHAR(160) NULL
managed_by_app BOOLEAN NOT NULL DEFAULT FALSE
```

字段含义：

- `source_type`
  - `user` 表示用户手动任务。
  - `app` 表示应用托管任务。
- `app_id`
  - 子应用标识，例如 `vocab`、`erc`。
- `app_task_type`
  - 子应用任务类型，例如 `vocab_today`、`erc_review`。
- `app_config_id`
  - 指向子应用初始化配置。
- `app_instance_key`
  - 用于去重或定位应用任务实例。对于每日重复任务，可为空或保存稳定任务 key。
- `managed_by_app`
  - 表示标题、业务含义和部分字段由子应用管理。

### 15.2 子应用初始化配置

可以为每个子应用建立自己的配置表，也可以先用统一表承载：

```text
app_task_configs
- id
- user_id
- app_id
- config JSONB
- status
- created_task_id
- created_at
- updated_at
```

如果 Vocab/ERC 的配置差异较大，长期更建议各自拥有明确配置表；统一表可作为第一阶段过渡。

## 16. API 设计草案

子应用初始化：

```text
POST /todo/app-tasks/vocab/init
POST /todo/app-tasks/erc/init
```

返回：

```json
{
  "config_id": "...",
  "task_id": "...",
  "status": "ready"
}
```

子应用状态查询：

```text
GET /todo/app-tasks/vocab/status
GET /todo/app-tasks/erc/status
```

返回：

```json
{
  "state": "ready",
  "task_id": "...",
  "completion_state": "...",
  "blocked_reason": null
}
```

开始专注：

```text
POST /todo/tasks/{task_id}/focus/start
```

或工作流阶段自动进入绑定的 `task_id`。后端根据任务来源返回对应专注适配器信息。

## 17. 迁移策略

建议分三步迁移：

1. 新增应用托管任务字段与初始化状态。
   - 不立即删除 `focus_work_type`。
   - Vocab/ERC 初始化后创建应用托管任务。

2. 让 Vocab/ERC 的“开始专注”改为基于 `task_id`。
   - 保留前端内容适配器。
   - 结束时写 `focus_logs` 和 `completion_records`。

3. 降低 `focus_app_work_logs` 的核心地位。
   - 可保留为兼容历史或业务快照表。
   - 新统计逐步基于 `focus_logs + tasks`。

## 18. 需要评审的关键决策

1. 应用托管任务默认是否显示在首页。
   - 推荐显示在“应用任务”分区，不混入普通任务。

2. Vocab/ERC 初始化是否允许创建多条任务。
   - 第一版推荐每个子应用先创建一条核心任务。
   - Vocab：今日单词。
   - ERC：ERC 复习。

3. 用户是否可以编辑应用托管任务标题。
   - 推荐默认不可直接改标题，但可以改计划、事件、提醒。

4. 应用任务完成是否必须由子应用确认。
   - 推荐必须由子应用适配器确认，避免用户绕过业务进度直接完成。

5. `focus_work_type` 是否立刻废弃。
   - 推荐不立刻废弃，先作为适配器类型保留；业务主身份迁移到 `task_id`。

## 19. 推荐第一版范围

第一版只做最小闭环：

1. Vocab/ERC 增加初始化状态和初始化入口。
2. 初始化后各创建一条应用托管重复任务。
3. 首页今日计划分区展示应用任务。
4. 应用任务可以进入统一专注工作。
5. 专注完成后写 `focus_logs` 和 `completion_records`。
6. 暂停/继续/放弃由弹窗壳统一承载。
7. 统计和成就先复用 `focus_logs + tasks` 的现有路径。

这样可以让业务模型先统一，同时避免一次性重写所有子应用内部逻辑。
